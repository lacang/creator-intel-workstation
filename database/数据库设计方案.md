# 数据库设计方案（P1）

> 对应任务书「P1：数据库建设」。采用 **SQLite**（轻量、单文件、零部署、适合个人工作站）。
> 配套文件：`database/schema.sql`（可直接 `sqlite3 workstation.db < schema.sql` 初始化）。
> 状态：**设计完成，待确认后建库并进入批量采集。**

---

## 一、核心设计原则（来自任务书，逐条落地）

| 任务书要求 | 本方案落地方式 |
|---|---|
| 建立 8 张表 | creators / creator_snapshots / works / work_snapshots / comments / content_analysis / trends / topic_opportunities |
| 主键、外键、唯一约束 | 每张表 `INTEGER PRIMARY KEY AUTOINCREMENT`；快照/评论表用外键级联 |
| 采集时间、来源链接、数据状态 | 每张表统一携带 `source` / `source_url` / `collected_at` / `data_status` 四件套 |
| **保留原始采集数据，分析结果不得覆盖原始数据** | 原始表含 `_raw_json` 存 API/网页原样响应；`content_analysis`、`topic_opportunities` 为**派生表**，只引用（`source_url` 指回原作品），绝不 UPDATE 原始表 |
| 事实、推断、建议分开 | `data_status` 枚举：`collected`(实测原始) / `derived`(分析派生) / `inferred`(推断) / `unverified`(未验证) / `needs_auth`(待授权) |
| 不收集与研究无关的个人信息 | `comments.author_handle` 仅存公开昵称，禁止存手机号/实名/私信等 PII |

## 二、表结构与职责

### 1. `creators` — 创作者主表（身份，稳定不变）
存放跨时间不变的身份字段：`platform`、`platform_uid`（平台内唯一，与 `platform` 组成唯一约束）、`handle`、`display_name`、`bio`、`avatar_url`、`category`（6 个观察方向之一）、`observation_tag`（入选理由）。
**不含粉丝数等时变指标**——时变指标全部进 `creator_snapshots`，避免主表被反复 UPDATE 污染原始快照。

### 2. `creator_snapshots` — 创作者指标时间序列
`follower_count` / `following_count` / `work_count` / `total_likes` / `avg_views` + `raw_metrics_json`。
唯一约束 `(creator_id, snapshot_at)`，保证同一时刻只一条；外键 `ON DELETE CASCADE`。

### 3. `works` — 作品主表（稳定元数据）
`platform` + `work_id`（bvid / aweme_id / note_id…）唯一约束；`creator_id` 关联创作者；`title` / `publish_time` / `url` / `cover_url` / `duration` / `work_type`。

### 4. `work_snapshots` — 作品指标时间序列
`play/like/comment/share/collect_count` + `raw_metrics_json`。唯一约束 `(work_id, snapshot_at)`。

### 5. `comments` — 评论
含 `parent_comment_id` 支持楼中楼；`author_handle` **仅公开昵称**（脱敏）；`is_sample` 标记是否入选需求研究样本。**不存 PII。**

### 6. `content_analysis` — 内容分析（派生，不回写）
对单作品深度拆解：`topic / title_eval / hook / structure / core_view / argumentation / emotion / narrative` + `raw_analysis_json`，记录 `analyst`(岗位) 与 `confidence`。
通过 `work_id UNIQUE` 一对一绑定作品，`source_url` 指回原作品，确保分析可追溯但**绝不覆盖 works/comments 原始数据**。

### 7. `trends` — 趋势
热榜/公开趋势入口（微博热搜、百度热榜、B站热门等）。`platform` / `trend_source` / `trend_time` / `rank` 唯一约束，`heat_value` 存热度值。

### 8. `topic_opportunities` — 选题机会（派生）
`based_on`(来源类型) / `need_ref`(引用 comments 或 content_analysis 的 id) / `trend_ref`(引用 trends id) / `supply_analysis` / `differentiation` / `personal_fit` / `series_potential` / `priority` / `status`。
> 注：`need_ref` / `trend_ref` 用 id 列表文本存，简单够用；若后续需多对多精确关联，建议改为关联表 `topic_need_link(topic_id, comment_id)` 等。当前为避免过度设计，先用文本引用。

## 三、可追溯性：数据审计员怎么用

- **任意结论可溯源**：`content_analysis.source_url` → `works.source_url` → 原始 `works._raw_json`；`topic_opportunities.need_ref` → 具体 `comments.id`（含 `source_url` + `collected_at`）。
- **批次审计**：建议扩展表 `collection_runs`（已附在 schema 末尾，不计入 8 表）记录每次采集的角色/来源/条数/状态，供审计员核对"计划 vs 实际"。
- **状态机**：所有记录用 `data_status` 标明`已完成 / 进行中 / 待授权 / 无法获取`，与任务书验收要求一致。

## 四、与 P0 实测结论的衔接

P0 实测决定了哪些源能真正落库：
- **可立即建采集**：`trends`（微博热搜、百度热榜、B站热门均已实测 200 真实数据）。
- **需登录态 cookie 才能落库**：`creators`/`works`/`comments` 的 B站部分（WBI 签名需先登录，见测试报告）。
- **受限/未验证，先不建采集任务**：抖音、小红书、视频号（不绕过反爬，标记为 `needs_auth` / `unverified`）。

## 五、备份策略（对应 `08_数据库备份`）
- 单文件 `workstation.db` 便于整体拷贝；每次批量采集后 `sqlite3 .dump` 或 `file:` 拷贝至 `08_数据库备份/YYYYMMDD_HHMM.db`。
- 不依赖云同步，按任务书「不越过云盘权限范围」本地留底。
- 实际落地改为：`tools/maintain.py` 每日用 sqlite3 backup API（WAL 安全）做一致性备份，保留最近 7 份。改动前另有 `workstation_pre_v2_*.db` 全量备份。

## 六、V2 更正与结构变更（2026-11-11 第二轮优化）

> **第四节是 P0 当时的历史结论，已被实测推翻，保留仅作证据链。** 正确结论见 `01_数据源/数据源测试报告.md` 第〇节与第七节。

| P0 历史结论 | 更正 |
|---|---|
| B站 `creators`/`works` 需登录态 cookie | **错误**：`ranking/v2`、`popular` 每条作品免登录自带 `owner(mid/name/face)` + 完整 `stat`，已稳定建成 455 创作者 / 525 作品 / 11196 指标快照 |
| 抖音受限、标记 `needs_auth` | **部分更正**：抖音官方热点榜 `/aweme/v1/web/hot/search/list/` 免登录稳定返回 50 条，并有独立的 `douyin_ies` 镜像源做交叉校验；作品/账号明细仍不可采（官方硬约束不变） |
| `comments` 待采 | 按合规要求**刻意保持为空**（PII），表结构保留 |

### 6.1 V2 结构变更（**原有 8 表结构未改**）

| 变更 | 类型 | 用途 |
|---|---|---|
| `source_catalog` | 新表 | 数据源目录：名称/平台/分级/间隔/提供内容/合规声明，看板与审计直接查 |
| `trends.heat_available` | `ALTER ADD COLUMN` | 区分「真实热度 0」与「平台不提供热度」（网易/知乎），避免把设计口径误判成缺陷 |
| `collection_runs.items_seen` | `ALTER ADD COLUMN` | 区分「看到」与「真实新增」；`items_collected` 自 V2 起只记新增（修掉虚报） |
| 7 个索引 | `CREATE INDEX IF NOT EXISTS` | `work_snapshots(snapshot_at)`、`trends(trend_time,platform)`、`collection_runs(source,run_at)` 等，避免高频刷新全表扫描 |
| `creator_snapshots.source` | 取值变更 | V2 起统一为 `aggregate`（所有作品源入库后聚合一次）；历史分片记录不改写 |

全部用 `IF NOT EXISTS` / `ADD COLUMN` / 新表实现，已有库平滑升级。

### 6.2 保留策略

2 分钟粒度下历史时序明细会持续膨胀，故每天清理一次：`trends` 7 天 / `work_snapshots` 与 `creator_snapshots` 30 天 / `collection_runs` 30 天 / `keyword_snapshots` 90 天。**只删时序明细，不删主表与派生结论**（`works`、`creators`、`content_analysis`、`topic_opportunities` 永久保留）。详见 `00_项目管理/系统架构与运维.md` 第五节。
