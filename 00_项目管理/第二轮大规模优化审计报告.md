## 三、审计发现与修复（逐条对应）

### 3.1 逻辑缺陷

| # | 问题 | 实测证据 | 修复 |
|---|---|---|---|
| **A1** | `ingest_creator_snapshots()` 挂在 `ingest()` 内，每个含作品的源都调用一次；SQL 按 `snapshot_at` 聚合「当时已入库」的快照 + `INSERT OR IGNORE`，导致同一轮创作者指标被切成三段 | 历史 `source` 分布：`bili_rank 4894 / bili_popular 2225 / bili_search 1278`；末轮 173 条作品快照本应覆盖 166 个创作者，但每个 UP 主的 `total_views` / `work_count` 只算到首次插入时的部分作品 → 看板「创作者榜」排序系统性失真 | 移到 `run_once()` **所有源入库之后统一调用一次**，先删本轮旧值再全量重算，`source='aggregate'`。实测末轮 `aggregate 214 条 / 分片 0 条` |
| **A2** | `ingest_work()` 恒定返回 1，即使 `works` 只是 UPSERT 更新、`work_snapshots` 被 `INSERT OR IGNORE` 忽略；`collection_runs.items_collected` 因此虚报 | 14:05 轮：`bili_popular` 报 60 条，真实新增快照 **43** 条（17 条与排行榜同 bvid 重复） | 返回 `cur.rowcount`；新增 `items_seen` 列区分「看到 / 真正新增」；状态判定改为「接口正常且看到数据即成功」，不再把全重复误判成 blocked。看板显示 `43 / 60` 并注明属正常 |
| **A3** | 跨平台共振用「整句去标点后完全相等」，各平台措辞不同导致几乎失效，**抖音完全不参与** | 优化前末轮 152 条热点只命中 **5 组**，全部是微博+百度；抖音参与 0 组 | 新增 `tools/textmatch.py`：精确归一化 + **受控模糊**（共享 ≥3 汉字的 4 字连续片段、排除功能词套话、每个片段最多连接 2 组防全连通）。模糊簇带 `evidence`（共现片段）与 `match='fuzzy'`，**在看板和派生表里显式标注为推断并降级 priority**。实测末轮 23 簇（精确 6 / 模糊 17），抖音参与 8 簇；选题表含抖音 32 条 |

## 五、实时性：分级调度而不是无脑提频

单纯把 cron 从 5 分钟改成 1 分钟会让 B站搜索等风控敏感接口频繁 412、数据库迅速膨胀。因此采用**每源独立间隔**：

```
cron 每 2 分钟触发 ws_maintain.sh
  ├─ 快线 120s ：8 个热榜/新闻源（轻量、直接决定「现在该追什么」）
  ├─ 慢线 300s ：B站排行榜 / 热门 / 分区榜（含作品指标快照）
  ├─ 慢线 600s ：B站关键词搜索（WAF 最严，单独降频）
  └─ 日更 3600s：百度垂直分榜 / B站入站必刷（变化极慢）
```

- 未到间隔的源写一条 `status='scheduled_skip'` 的 `collection_runs` 记录后跳过，**审计链完整**；看板显示「按期间隔跳过 = 未到间隔，不是失败」，源成功率分母也排除它。
- 数据源目录 `source_catalog` 把「哪些源、多久采一次、提供什么、合规口径」写进库，看板直接查，不靠读代码猜。
- **数据保留**：`prune_db()` 每天清理一次历史时序明细（trends 7 天 / snapshots 30 天 / runs 30 天 / keyword 90 天），只删明细，**不删主表与派生结论**，防止 2 分钟粒度把库撑爆。
- **热更新防护**：cron 入口先做语法预检（见 3.2）。
- **自愈链路保持**：`@reboot` + shell 启动钩子 + 请求触发补采 + 实时健康计算（阈值统一为 600s）不变。

## 八、遗留风险与诚实边界

1. **休眠期间的空窗仍无法补造**：沙箱休眠会清掉包括 cron 在内的全部进程，热榜是实时数据，冻结期间没有任何进程能运行。能做的仍是「恢复后尽快自愈」+「停滞如实可见」，本轮未粉饰。历史 2 段空窗继续在看板保留。
2. **模糊共振是推断，不是平台确认的事实**：已用 `match='fuzzy'`、共现片段、优先级降级、「需人工核实」三重标注；即便如此，个别簇可能把同一场颁奖礼的不同人物话题连在一起（实测「高叶获奖」与「朱一龙看梁家辉获奖」同簇），**需人工二次筛选**。看板一句话结论已改为优先引用精确共振。
3. **历史记录 `items_seen` 为 DEFAULT 0**：该列是本轮后加的，345 条历史审计记录没有这个字段。按「不改写历史」原则**未回填**，审计工具把新旧口径分开统计并如实标注。
4. **不改历史数据**：A1 修复只影响新轮次；历史 8397 条分片 `creator_snapshots` 保留原样，是当时实现的真实记录。
5. **未采购任何商业/官方企业 API**：理由不变（真人实名/企业资质/对公付款不可代办，且付费不能拿任意第三方账号明细）。表结构与采集框架仍预留接口。
6. **抖音仍是「热点榜」而非「作品/账号明细」**：这是合规公开源能给到的上限。抖音主入口已通过双源校验 + 单独列 + 镜像源加固。
