### 命令


## 四、口径调整与边界（诚实说明）

原任务书 P2/P3 要求「观察指定 30 个他人账号 / 200 条他人作品明细」。经官方渠道调研（见 `01_数据源/官方渠道调研报告.md` 第三、五节）确认：抖音开放平台 API 只服务「授权用户自己的账号」，个人主体不可申请，**纯官方渠道无法读取任意第三方账号明细**；商业 SaaS 需真人实名注册与付费，AI 无法代完成，且其数据来源合规边界需另行评估。

因此本阶段将 P2/P3 落地为「**公开榜单上的创作者与作品实时情报**」：数据源合规、可持续、无需任何凭证，覆盖创作者身份、作品元数据、全量互动指标与逐轮增长。`comments` 表按合规要求留空。若后续确需「指定竞品账号全量明细」，表结构与采集框架已预留接口，需用户本人完成商业服务采购后接入。

## 五、合规红线（全程未越界）

仅访问免登录、公开可访问的官方榜单 / 热点接口；不携带任何登录态或 cookie；不生成 / 伪造 a_bogus、X-Bogus、WBI 等反爬签名；不触发或绕过验证码 / 二次验证 / 设备校验；不采集含实名 / 手机号等 PII 的数据。

## 七、关于「可以花点钱」的执行说明

本轮**没有发生任何付费**，也未注册 / 试用任何商业服务。原因不是缺少授权，而是：

1. 本系统以**零成本合规公开源**即可真正跑起来并持续更新，无需采购即达成「实时创作者数据库」目标；
2. 商业 SaaS（蝉妈妈 / 飞瓜等）与官方企业 API 均需**真人实名注册、企业资质 / 对公付款**，AI 无法代完成，不能假装已采购；
3. 官方 API 仍不提供「任意第三方账号明细」，付费也无法改变该硬约束。

接口与表结构已预留。可选增强（非阻塞，需用户本人一步操作）：注册企业主体申请官方免费大盘 Scope，或采购商业数据服务并索取数据来源合规说明。两者均不影响当前系统持续运行。

## 九、第二次中断与「沙箱休眠」根因（2026-11-11 10:28 复盘）

### 9.1 事故（如实记录，不粉饰）

10:28 用户回来说「我看看」，核查发现系统**又停了**：

| 项 | 10:28:59 实测 |
|---|---|
| 维护任务最后执行 | 09:35:01 |
| 数据库末轮 | 09:35:01（共 17 轮） |
| 看板服务 | HTTP 000（进程、端口全无） |
| 空窗 | 09:35 → 10:28 约 54 分钟 |

`uptime` 显示 `up 7 min`——**沙箱在此期间休眠、约 10:22 被唤醒重启**。crontab 配置还在，但 cron 守护进程与看板服务都被清掉且恢复时不自动拉起。这是**平台级限制**：休眠会清掉含系统 cron 在内的全部进程，用户态进程无法保证"休眠期间仍在跑"。

同时暴露一个更该修的问题：`logs/health.json` 是维护任务写的一次性快照，cron 停摆后它冻结在 `healthy=true / 距上次 0.3 分钟`——**服务都挂了看板还在显示绿**，等于"停了却没人知道"的翻版。

### 9.2 三层加固（均经实际演练验证）

| 层 | 机制 | 文件 | 作用 |
|---|---|---|---|
| L1 实时健康 | 健康状态改为**看板每次请求直接从 DB 末轮时间实时计算**，不再读静态 `health.json` | `tools/dashboard.py::data_continuity()` | 无论调度器死活，页面显示的都是此刻真值 |
| L1' 前端防呆 | 页面用 `浏览器当前时间 − 末轮采集时间` 重算滞后，>15 分钟自动变红并给出告警 | `tools/dashboard.py::drawContinuity()` | 静态快照、服务挂掉、cron 停摆时都不再显示假的绿 |
| L2 请求自愈 | 服务存活但数据 `stale` 时，用户一访问 `/api/all` 即在守护线程补采一轮（120s 节流 + 并发锁、非阻塞） | `tools/dashboard.py::maybe_self_heal()` | cron 死了但服务还在时，访问即续数据 |
| L3 会话钩子 | 系统级 shell 启动钩子：恢复后任意一次 shell 活动自动检查并拉起 cron 与服务，90s 节流、`setsid` 独立会话、完全后台非阻塞 | `/usr/local/bin/ws_watchdog.sh` + `ws_watchdog_run.sh` + `/etc/profile.d/zz-workstation-heal.sh` + `/etc/zsh/zshenv` | 覆盖"休眠恢复后无人拉起"这一根因 |
| L3' 双保险 | crontab 增加 `@reboot /usr/local/bin/ws_maintain.sh` | crontab | 系统重启时主动跑一次完整维护 |

### 9.3 故障演练（不是口头声称）

做了一次**彻底停摆演练**：`pkill -x cron` + 按端口杀掉看板服务（确认两者均停），删除节流标记，然后只触发一次普通 `login shell`（模拟"用户回来发消息"）。

- **第一次演练失败**：`ws_watchdog_run.sh` 新建但未 `chmod +x`，`setsid` 调起时 permission denied 静默失败，日志为空；且 `service cron stop` 未真正停掉 cron，导致"5 秒恢复"其实是 cron 自己跑维护顺带拉起的服务 —— 已如实推翻、不算通过。
- **修复后重做**：确认 cron 与端口双停 → 一次 login shell → **第 4 秒自动恢复**（cron 存活、首页 HTTP 200），`/tmp/ws_watchdog.log` 留有 `heal:cron_restarted` 硬证据，全程未手动兜底。

### 9.4 仍须诚实说明的边界

- **休眠期间的空窗无法补造**：热榜是实时数据，VM 冻结期间没有任何进程能运行，这是平台限制，不是代码能根治的。能做的是"恢复后尽快自愈"和"停滞如实可见"。
- **不会再把静态快照当健康真值**：`health.json` 仍由维护任务写（用于历史空窗审计），但看板健康状态一律实时计算 + 前端二次核对。
- 看板「数据连续性」面板现显示「页面实时核对」时间与「距今已 X 分钟」，超过 15 分钟即红字告警，打开页面即可自证，不必依赖任何口头声明。

### 9.5 恢复后状态（10:49 核验）

cron 存活、crontab 含 `*/5` 与 `@reboot`、4 个钩子文件就位、服务跑最新代码（`/api/version` 指纹与文件 mtime 一致）、实时接口 14 字段齐全、`continuity.live=true`、质量自检 90 分 0 错误、静态快照含防骗逻辑。数据库累计 **20 轮 / 3033 热点 / 2963 作品快照 / 312 关注词快照 / 120 审计**，历史空窗 2 段如实保留。

## 十一、V3 阶段：从「监视器」到「主持人智库 + 起号准备工作台」

> 触发：用户诚实复盘——作为**尚未起号的电台/播客主持人**，原系统只回答「今天什么热」，
> 不能回答「我作为主持人该准备什么、攒哪些可复用的框架和选题」，赋能有限。
> 用户明确：电台/播客主持背景；希望系统以「起号准备工作台」为首要入口。

### 11.1 关键认知修正（重要）

- 之前 `config/creator_profile.json` 把用户画像**瞎猜成「逸博故事多 / 故事向」**，与真实身份不符。
  已更正：电台/播客主持人，尚未起号，转型个人创作者。
- 原系统数据是「易逝」的（trends 7 天清理、看完即弃），与「智库」方向相反。
  新增独立 `knowledge_base` 表承载「耐久」沉淀，不被清理脚本丢弃。

### 11.2 本轮交付

| 模块 | 内容 |
|---|---|
| `config/host_profile.json`（新增） | 电台主持专属配置：5 项可迁移能力 + 5 个内容框架 + 6 类赛道信号词与电台视角角度 |
| `config/creator_profile.json`（修正） | 删除错误画像，与 host_profile 对齐 |
| `tools/knowledge.py`（新增） | 智库沉淀引擎：每轮把命中信号词的热榜话题，按主持人能力匹配后写成带电台视角角度的条目；跨轮/跨平台复现自动晋升常青 |
| 3 张新表 | `host_assets` / `content_frameworks` / `knowledge_base` |
| `tools/collector.py` | `run_once` 末尾调用 `knowledge.incubate`；`collector.PRIMARY_SOURCE/PRIMARY_SOURCES` 成为简报+智库的唯一主源口径 |
| `tools/dashboard.py` | 首屏新增「起号准备工作台·主持人智库」面板（定位卡/能力库/框架库/常青选题库/准备清单）；`POST /api/kb/<id>/promote` 手动策展 |
| `tools/verify.py` / `tools/audit.py` | 第 11 组 / G 组：智库播种、沉淀增长、晋升机制 |
| `00_项目管理/主持人智库设计方案.md`（新增） | 本方向设计文档 |

### 11.3 实测证据

- 连续 6 轮验证：第 3 轮起跨轮复现话题自动晋升「常青」（52→54 条），`durability` 爬升至 8。
- 终检：审计 **22 PASS / 1 WARN / 0 FAIL**（WARN 为测试强制全源每轮跑、末轮无 scheduled_skip 所致，非缺陷）；质量 95 分 0 错误。
- KB 累计 72 条：常青 54 / 孵化 18 / 待拍 0；6 大类别全覆盖（人物命运线 34、社会观察 19、生活叙事 10、观点对话 10、突发现场 6）。
- `POST /api/kb/<id>/promote` 实测可把 validated → ready（测试后已回退，待用户自行策展）。

### 11.4 沉淀机制一句话总结

> 热榜是「易逝」的，智库是「耐久」的。同一话题跨轮/跨平台反复出现，其洞察留在
> `knowledge_base`，原始热榜清掉也不影响——这就是「数据怎么沉淀成智库」。
